# 自动化测试工作流

## 适用场景

- 用户要求搭建前端自动化测试工程。
- 用户要求将稳定人工用例改写为 Playwright、Vitest 或组件测试。
- 用户要求执行自动化命令并输出测试报告。
- 用户要求治理 flaky、选择器不稳定、登录态不稳定、测试数据污染、CI 失败等自动化问题。

## 自动化前置输入

开始落地前尽量确认：

- 项目目录、技术栈、包管理器和启动命令。
- 测试环境地址、登录方式、测试账号和角色权限。
- 是否允许接口造数、清理数据、修改测试数据、删除 `QA_` 数据。
- 运行范围：`smoke`、`regression`、`full`、指定 spec。
- CI 运行环境、浏览器范围、报告产物保留策略。

缺少输入时输出环境变量和阻塞清单，不用人工接管替代自动化。

## 自动化分层

Playwright E2E 适合：

- 页面可达、URL、菜单、按钮可见性。
- 登录、列表查询、分页、空状态。
- 新增、编辑、状态变更后的数据持久化。
- 表单必填、格式校验、联动规则、权限状态。
- 关键用户路径中的成功、失败和空状态。

接口辅助适合：

- 准备可重复测试数据。
- 清理 `QA_` 前缀数据。
- 校验保存、删除、状态流转后的后端结果。
- 避免 E2E 在 UI 上做大量低价值准备动作。

组件测试适合：

- 复杂表单联动。
- 富文本、上传组件、动态选项。
- 权限计算、字段映射、状态展示。
- 不需要真实浏览器路由和后端数据的前端逻辑。

保留为非自动化或待确认：

- 主观视觉美观判断。
- 需要验证码、人工审批、第三方人工操作的流程。
- 无法稳定造数或清理的共享数据场景。
- 生产或准生产环境上的高风险删除、支付、权限变更。

## 自动化转化步骤

1. 选择稳定、客观、重复价值高的用例。
2. 明确前置数据、账号、权限和清理方式。
3. 补齐页面 `data-testid` 或选择稳定 locator。
4. 封装 Page Object、fixture 和数据工具。
5. 编写 spec 并加 `@smoke` 或 `@regression`。
6. 使用接口响应、页面状态、URL 和数据持久化做断言。
7. 配置截图、trace、视频和 JSON/HTML 报告。
8. 将不稳定依赖记录为待治理项，不强行纳入阻断。

## 自动化报告

执行结束后输出：

```markdown
# 自动化测试报告

**项目：** 项目名称
**环境：** 测试环境地址
**命令：** npm run test:e2e:smoke
**范围：** smoke / regression / full / 指定 spec
**结论：** 通过 / 不通过 / 阻塞 / 有条件通过

## 汇总
- 总数：
- 通过：
- 失败：
- 阻塞：
- 跳过：

## 失败
- 用例：
- 失败原因：
- 证据：
- 修复建议：

## 阻塞
- 阻塞项：
- 影响范围：
- 需要补充：

## 产物
- HTML Report：
- JSON Result：
- Screenshot：
- Video：
- Trace：
```

## 阻塞判定

- 缺少测试账号、验证码无法自动处理、无测试数据授权：阻塞。
- 页面元素没有稳定定位且无法安全补 `data-testid`：阻塞或先补选择器。
- 写操作没有 `QA_` 数据或清理策略：阻塞。
- 独立自动化会话与手工浏览器数据不一致：阻塞，优先解决登录态和数据准备。
- flaky 未定位原因：隔离，不作为发布阻断。
